# 算力与硬件规划

## OPD 的算力花在哪里

一个 OPD step 有四块开销：

| 环节 | 做什么 | 性质 |
|---|---|---|
| 学生 rollout | 学生逐 token 生成回答 | decode，受显存带宽限制 |
| 教师打分 | 教师对"prompt + 学生回答"做**一次 prefill**，返回 logprob | prefill，受算力限制；**不需要 decode** |
| 重算学生 logprob | 训练引擎对同样的序列做一次前向 | 前向 |
| 更新 | 反向传播 + 优化器 | 最重，受算力和显存限制 |

**教师只做 prefill，不生成文本。** 这是 OPD 比"让教师生成数据"便宜得多的原因，也是一张 96GB 的卡就能放下 27B–32B 教师的原因。

一个真实的冒烟测试（学生 Qwen3.5-4B，教师 27B，各占一张卡，16 道 GSM8K 题，参数和优化器都 offload 到 CPU）中，一个 step 的耗时：

| 环节 | 耗时 |
|---|---|
| gen（学生采样 + 教师 prefill，流式进行） | 6.24 s |
| old_log_prob（训练引擎前向） | 13.59 s |
| update_actor（反向 + 优化器） | 18.69 s |
| update_weights（新权重同步到 vLLM） | 2.23 s |
| **合计** | **40.8 s** |

教师打分是流式进行的：一条回答生成完就立刻发给教师，不等整个 batch，所以它的耗时被藏在了 gen 里。这个例子里最慢的反而是训练部分，因为开了 CPU offload。详见[verl 源码走读](../frameworks/verl-walkthrough.md)。

## 显存估算

按 BF16 计算，每个参数 2 字节：

| 模型 | 权重（BF16） | 全参训练（权重 + 梯度 + Adam，约 16 字节/参数，不含激活） |
|---|---|---|
| 0.6B | 约 1.2 GB | 约 10 GB |
| 1.7B | 约 3.4 GB | 约 27 GB |
| 4B | 约 8 GB | 约 64 GB |
| 8B | 约 16 GB | 约 128 GB（需要分片或 offload） |
| 27B–32B | 约 54–64 GB | — （只当教师） |

- 教师只做推理，显存主要是**权重 + 少量 KV cache**；FP8 版本的权重再减半；
- 学生要同时放 rollout 引擎（vLLM）和训练引擎（FSDP / Megatron），两者通常分时共用一张卡；
- LoRA 能大幅降低训练显存，而且 OPD 对 LoRA 比较友好（见[标准配方](recipe.md)）。

## 学生和教师怎么放

| 方式 | 做法 | 适合 |
|---|---|---|
| **独立教师池** | 教师单独占几张卡，作为推理服务 | 最常见；verl 的 `distillation.n_gpus_per_node`、ms-swift 的 `--teacher_model_server` |
| 同卡共存 | 教师和学生挤在同一张卡上，限制各自的显存占比 | 卡少、模型小 |
| 离线缓存 | 学生一次性生成 rollout，教师一次性算好 logprob 存盘，训练时读取 | 卡少、教师大；见 [Semi-OPD](../frontier/efficiency.md) |
| 按需加载 | 教师权重放在分布式存储里，用到时再分片加载 | 教师很多、很大；DeepSeek-V4 的做法，见[工程优化](../frameworks/infra.md) |

## 以 H20 为例

H20 的特点是**显存大、算力弱**：<span class="unverified">⚠️</span>

| 项目 | 数值 |
|---|---|
| 显存 | 96 GB HBM3 |
| 显存带宽 | 约 4.0 TB/s |
| BF16 算力（稠密） | 约 148 TFLOPS，约为 H100 / H200 的 1/6.7 |
| FP8 算力 | 约 296 TFLOPS |

所以 H20 很适合**推理类**的工作（学生 rollout、教师打分），训练会偏慢。规划时：

- 学生尽量小（0.6B–4B，最多 8B），优先考虑 LoRA；
- 上下文控制在 16K 以内；
- 教师可以大一些，因为它只做 prefill。

几种卡数下的参考方案：

| 卡数 | 学生 | 教师 | 布局 |
|---|---|---|---|
| 1 张 | 0.6B–1.7B | 1.7B–4B，或自蒸馏 | 同卡共存；或者先离线缓存教师 logprob（Semi-OPD），训练时教师不常驻 |
| 2 张 | 1.7B–4B | 8B–32B | 卡 1：学生 rollout + 训练；卡 2：教师推理服务（上面冒烟测试的布局） |
| 8 张 | 4B–8B | 32B（TP=2）或多个领域教师 | 2–4 张给教师池，其余给学生训练和 rollout |

## 省算力的办法

- **Semi-OPD**：学生 rollout 和教师 logprob 都只算一次，反复复用，报告训练提速最多 11.4 倍 <span class="unverified">⚠️</span>；
- **提前停止 / 截断**：轨迹后段的信号本来就不可靠，可以不生成、不打分（STRIDE、前缀截断）；
- **生成 batch 与训练 micro-batch 解耦**：把多个梯度累积步的 prompt 攒起来一次性交给 vLLM，提高生成吞吐（TRL 报告 64 步累积时提速 41.7 倍）<span class="verified">✅</span>；
- **教师服务端批处理 + 二进制传输**：见[工程优化](../frameworks/infra.md)；
- **每题少采几条**：OPD 不需要组内比较，每题 1–4 条即可。
