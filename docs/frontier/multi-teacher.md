# 多教师 OPD

## 为什么要多教师

一个模型要同时擅长数学、代码、Agent、指令跟随、安全……如果把这些能力的 RL 混在一起训练，常常出现"一项涨、一项跌"的跷跷板问题。多教师 OPD 的思路是：

1. **先分开**：每个领域各自训练一个专家（SFT + RL），互不干扰；
2. **再合并**：用 OPD 让一个学生在自己的轨迹上向对应领域的专家学习。

和其他合并方式的对比：

| 方式 | 问题 |
|---|---|
| 权重合并（model merging） | 参数空间直接平均，各专家的峰值能力难以保住 |
| 混合 RL | 多个奖励互相拉扯，跷跷板问题 |
| 顺序训练 | 后训的领域会让先训的领域遗忘 |
| 用各专家的数据做 SFT | off-policy，有 exposure bias |
| **多教师 OPD** | 学生 on-policy，在 logits 层面对齐对应专家；新增教师不用改流程 |

## 怎么路由

每道题属于某个领域，交给对应的教师打分。

- DeepSeek-V4：对每个专家的 reverse KL 加权求和，$\mathcal{L} = \sum_i w_i \cdot \mathrm{KL}(\pi_\theta \,\|\, \pi_{E_i})$，学生按任务上下文向相关专家对齐；<span class="verified">✅</span>
- MiMo-V2-Flash：按题目所属领域选教师 $\pi_{\text{domain}_x}$，再叠加 GRPO 结果奖励；<span class="verified">✅</span>
- verl：用数据里的 `data_source` 字段（可配置）路由，每个教师配一个 `key`；要打开 `data.shuffle`，否则会长时间只路由到同一个教师；<span class="verified">✅</span>
- tinker-cookbook：每个数据集配自己的教师和 batch 大小，训练时把各数据集的 batch 拼起来。<span class="verified">✅</span>

## 教师之间要兼容

2607.24720 在受控的多轮规划环境里发现 <span class="unverified">⚠️</span>：

- 多教师 OPD 通过收敛到一个**共享的规划模式**来整合能力；
- 教师模式**兼容**：带来跨环境的泛化；
- **部分重叠**：能支持持续学习；
- **完全冲突**：产生严重的干扰。

## 工具调用场景的陷阱：过度调用

2607.07050 研究了一个双教师设置：一个"回答教师"擅长直接回答，一个"工具教师"擅长调用工具。<span class="unverified">⚠️</span>

**现象**：普通的 GKD 提高了工具调用的召回率，但也让学生在本该直接回答的问题上调用工具。

**原因：关键决策 token 被 top-K 截断漏掉了。** 回答教师的 top-32 覆盖了 99.99% 的概率质量，但在 1,500 条审计样本里，只有 0.4% 包含"切换到工具调用"的那个 token（top-256 也只覆盖 52.2%）。被截掉的 logit 拿不到直接梯度，于是工具教师不断强化"调用工具"的入口，回答教师却几乎从来没法反向施压。作者称之为"决策关键支持遗漏"（decision-critical support omission）。

**修法与代价**：在每个回答位置都把工具调用 token 补回支持集（三个随机种子）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 完整生成中的过度调用率 | 14.2±2.1% | 3.7±0.5% |
| 工具调用召回率 | 91.5±1.7% | 79.1±1.7% |
| 多轮完全成功率 | 7.0±0.3% | 3.4±0.5% |

过度调用大幅下降，但正确的工具调用和多轮成功率也跟着下降。作者把它描述为**保守性和能力之间的取舍**，而不是免费的提升。只在第一个位置补回 token，能修正首 token 的入口，但大多只是把调用推迟了。

**启示**：多教师时，要特别检查那些"决定走哪条分支"的 token 是否在截断后的支持集里。

## 合并之后要逐领域对比

MiMo-V2-Flash 的结果显示，多教师 OPD 在大多数领域追平或略超最强教师，但长程搜索 Agent（BrowseComp −6.3）和创意写作（−3.9）有明显回退。合并之后，一定要逐个领域和对应的最强教师比较。
